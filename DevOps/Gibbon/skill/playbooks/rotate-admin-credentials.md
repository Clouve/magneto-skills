# Playbook: Rotate Admin Credentials

Three distinct things that can be "rotated" here, with very different procedures:

1. **Gibbon admin user password** — the `GIBBON_PASSWORD` the tenant uses to log into Gibbon's UI as the first admin.
2. **Gibbon DB credentials** — the `DB_PASSWORD` Gibbon uses to connect to `gibbon-mysql`.
3. **The tenant's Anthropic API key** — stored on disk at `$HOME/.claude_api_key` in the AI Studio container.

Pick the right one before doing anything.

## 1. Rotate the Gibbon admin user password

**Do this in the Gibbon UI. Do not touch the DB.**

The tenant:
1. Logs into Gibbon as an admin (if they remember the old password) OR uses the **Forgot Password** flow from the login page (sends a reset email to the admin address).
2. Navigates to their user profile → **Change Password**.
3. Sets the new one.

If they're locked out (forgot password, no mailer configured):
- **Preferred:** have them configure the mailer first (System Admin → Email), then use Forgot Password. This is also a good outcome in its own right — notifications will start working again.
- **Fallback with tenant ack:** an admin user's password hash lives in `gibbonPerson.password`. Gibbon uses its own hasher (check `Gibbon\Services\PasswordEncoder`). You can reset it by having the tenant run the password-reset script upstream Gibbon ships, but **we do not have a CLI for this in the app**. Do not fabricate a reset SQL statement — a MySQL `UPDATE gibbonPerson SET password='...'` with a hash you generated by hand will almost certainly not match Gibbon's expected format, and recovery becomes harder.

**Refuse to help if:** the user asking for the password reset can't prove they're the tenant admin (e.g. they're saying "my colleague is locked out, can you change his password for me?"). That's out-of-band identity verification, not Claude's call.

## 2. Rotate the Gibbon DB password

The image auto-syncs `config.php` from env vars on every restart. Use that.

### Procedure

1. **Take a backup first.** A DB credential rotation doesn't destroy data, but if Gibbon can't reach MySQL after restart for any reason, you want a rollback point.

2. **Update the password in MySQL.** Only works if the caller has root or sufficient GRANT access:
   ```bash
   # Through Clouve ops or a user with MYSQL_ROOT_PASSWORD:
   mysql -h "$GIBBON_DB_HOST" -u root -p"$MYSQL_ROOT_PASSWORD" -e \
     "ALTER USER 'gibbon'@'%' IDENTIFIED BY '<new-password>'; FLUSH PRIVILEGES;"
   ```
   From AI Studio you usually don't have root. Escalate to Clouve ops.

3. **Update the app's env var.** `DB_PASSWORD` in the pod spec (for this app it's the `secret` type, Clouve-managed). Via the Clouve platform UI: rotate the secret.

4. **Restart the `gibbon` container.** On boot, `update-config.sh` reads the new `DB_PASSWORD` from env and rewrites `config.php`:
   ```
   sed -i "s/^\$databasePassword = .*$/\$databasePassword = '<new>';/" config.php
   ```
   (The script escapes `/` and `&` but not backslashes or single-quotes — keep generated passwords alphanumeric-plus-simple-symbols.)

5. **Verify.**
   ```bash
   # Connection works with the new password.
   MYSQL_PWD="<new>" mysql -h "$GIBBON_DB_HOST" -u gibbon gibbon -e "SELECT 1;"
   # Gibbon HTTP works (uses the new password from config.php).
   curl -sI http://gibbon/index.php | head -1   # expect "HTTP/1.1 200 OK"
   ```

### Do NOT

- Do NOT hand-edit `config.php` to change the password — the next container restart will sync env → file and overwrite your change, or worse, the sed will fail mid-rewrite and leave `config.php` broken.
- Do NOT put a password with `'` in it into `DB_PASSWORD`. Gibbon's `config.php` uses single-quoted PHP strings and the image's sed doesn't escape `'`.

## 3. Rotate the tenant's Anthropic API key

This is between the tenant and Anthropic — Clouve never stores, proxies, or sees the key.

The key lives in three possible places, resolution order per [apps/ai-studio/image/installer/chat/.bash_profile](../../../ai-studio/image/installer/chat/.bash_profile):

1. `$ANTHROPIC_API_KEY` env var injected at pod launch (from Clouve's `userConfigurable` secret).
2. `$HOME/.claude_api_key` file — persisted across restarts on the `ai-studio-home` volume.
3. In-terminal prompt at first session.

Plus:
4. AI Studio's web Preferences Panel.

### Procedure

Tenant path (don't do this for them):
1. Generate a new key at `console.anthropic.com/settings/keys`.
2. Either: overwrite `$HOME/.claude_api_key` with the new key, OR use AI Studio's Preferences Panel to update it.
3. Open a fresh terminal → Claude Code picks up the new key.
4. Revoke the old key at `console.anthropic.com/settings/keys`.

### Do NOT

- Print the key to chat, even redacted.
- Copy the key to anywhere outside `$HOME/.claude_api_key`.
- Send the key over any network endpoint other than `api.anthropic.com`.
- Assume the env var and the file agree. If they disagree, the env var wins on first boot, but once `.claude_api_key` exists it takes precedence for the terminal client per `.bash_profile`'s resolution order.
