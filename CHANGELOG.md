# Changelog

## Unreleased

- **moodle** (0.1.6): `scripts/verify-health.sh` reported RED on every Kubernetes deployment, from three bugs in its own code. The login-page probe went to `http://${MOODLE_HOST}`, and Moodle answers any host but its `wwwroot`'s with a 303: the probe now sends `Host:` with the host of `MOODLE_URL` (with an https URL the image sets `$CFG->sslproxy`, so the host is all Moodle checks). The code version came from a one-liner whose `$CFG` the remote shell expanded to nothing, and even quoted right it would have read the database's version: the script now reads `$version` from `version.php` on the sibling (`public/` first, as the image does), with the commands sent to `bash -s` on stdin, and compares versions as numbers (`2026042000.00` in the file, `2026042000` in `mdl_config`). The cron check did shell arithmetic on `MAX(timestart)`, a decimal column, and stopped with a syntax error: it now uses whole seconds. `reference/shell-access.md` gives the probe with the `Host:` header too. `tests/moodle-verify-health.test.sh` runs the script against fake `curl`, `mysql`, `sshpass` and `php`, with the remote commands run by a real bash.
- **ai-studio** (0.2.3), **gibbon** (0.1.3), **moodle** (0.1.5), **odoo** (0.1.3), **wordpress** (0.1.4): passwords are no longer in the AI Assistant's environment on new Magneto Agents. The agent keeps them in `/run/clouve/secrets.env`, and `clv-secret NAME` prints one. Skills reach every agent from git, and older agents still have the password in the environment and no `clv-secret`, so every command now fetches a password as `${NAME:-$(clv-secret NAME)}`. That works on both: an agent that has `NAME` never runs the second half. Each script that uses an agent-side secret loads it once near the top with `: "${NAME:=$(clv-secret NAME)}"`. The `:` keeps the line safe under `set -e`, and the line has no `2>/dev/null`, so `clv-secret`'s own messages ("waiting for the agent to finish connecting to its apps...", "NAME is not set on this server") reach whoever ran the script. Each `SKILL.md` says in its environment section that passwords aren't in the environment and that `clv-secret --list` shows the names. Lines that called a password "already in your env", or told the assistant to pass one as `$(printenv NAME)`, now describe `clv-secret`, and prose that only names a variable uses the bare name. In the WordPress playbooks and references, each `compgen -e | grep` step has a `clv-secret --list | grep` line for the passwords' names, and the script messages that sent the reader to `compgen` for a password's name say `clv-secret --list`. moodle's and wordpress's `learnings.md` get the "Secrets. Ever." line that gibbon's and odoo's already had. `CLAUDE.md` has the secrets contract. `tests/skills-env-values.test.sh` fails on a bare `$NAME` of an agent-side secret, a script without its loader line, `printenv` of a secret, and prose that calls a password "already in your" environment.
- **moodle** (0.1.4): the skill said that plugins installed at runtime are wiped on the next pod restart. They never were: the code tree is the persistent `moodle-www-data` volume. With the Moodle image's new upgrade (magneto `apps/moodle/image/installer/upgrade.sh`), they also survive a Moodle version bump. The upgrade copies them into the new code, and holds a plugin back in `/var/www/html/clouve/upgrade-stash/<UTC time>/`, with the reason in the container log, when the new Moodle ships it, its `version.php` says it won't work with the new Moodle, or Moodle's upgrade fails twice with the added plugins in place. The `install-plugin` playbook and `reference/shell-access.md` now say so, the playbook says how to put a held-back plugin back, and it links to the image's Dockerfile by URL.
- **ai-studio** (0.2.2): the skill sent the assistant to `clouve-ops@ai-studio`, a name that resolves only under docker-compose. On Kubernetes the workspace is `tkt-<id>-ai-studio`, so every SSH step the skill gave failed there. It now uses `${AI_STUDIO_HOST}`, which the Magneto Agent sets at start like the other skills' `*_HOST` variables, and confirms the variable with `compgen -e | grep -i studio`, which lists names only. `tests/ai-studio-host.test.sh` fails on any bare `ai-studio` SSH target or hostname in the ai-studio and mern plugins.
- **moodle** (0.1.3), **wordpress** (0.1.3): the steps that discover the injected variables list their names only. `env | grep -i moodle_db` and the wordpress `env | grep -iE 'wordpress|mysql|maria|host'` printed the matching values, database passwords included, into the assistant's context and onto the customer's screen. They are now `compgen -e | grep ...`, in the playbooks, references and the three wordpress scripts' error messages, and wordpress's `SKILL.md` says to pass a value as `$(printenv NAME)` without printing it. `tests/skills-env-values.test.sh` fails on `env | grep`, `printenv | grep`, `set | grep`, a bare `env` or `printenv` line, or `export -p` in any skill. moodle also gains operating principle 12 and a note in the `rotate-admin-credentials` playbook for the kit's Gibbon-synced `auth = 'db'` users: `reset_password.php` only finds `auth = 'manual'` accounts, so set their password with `update_internal_user_password()` and then clear the `create_password` preference. The External Database sync tags every user it creates with it, and Moodle's "Send new user passwords" task replaces that password with a random one at its next run (every minute on Clouve) and emails it. On the rig, the password the assistant showed for a new student stopped working 40 seconds later. `tests/moodle-synced-user-password.test.sh` fails when a moodle file sets a password without clearing it.
- **odoo** (0.1.2): fixed the backup and install steps that stalled the AI Assistant on 2026-10-19. The playbooks ran `scripts/backup.sh` from `/var/lib/odoo/scripts/`, which no Odoo container has. The assistant now pipes the skill's own copy into the Odoo container (`sshpass -e ssh ... "sudo bash -s -- <db>" < /clouve/skills/odoo/plugin/skills/odoo/scripts/backup.sh`), and the script now runs there: `odoo db dump` with the config in `ODOO_RC`, then a check that the ZIP holds `dump.sql`, `manifest.json` and the filestore; a failed dump or check leaves no file behind. Every `odoo db` command takes `ODOO_RC=/etc/odoo/odoo.conf` instead of `-c`: Odoo 19 rejects `-c` after `dump` or `load`, and `sudo` over SSH drops the image's own `ODOO_RC`. `restore.sh` got the same fix, and the restore playbook now runs it in the agent, where it lives. Module installs run while Odoo keeps serving (checked with `crm`: the live server reloads its registry by itself), and the pod restarts are gone, since the agent has no kubectl and the customer's dashboard has no restart button. When new third-party code needs a restart, the assistant sends `SIGHUP` to Odoo (PID 1), which re-executes itself in the same container. Also fixed: `odoo shell` lines without `-c` (they couldn't reach the database under `sudo`), `pg_dump` and `psql` run as `sudo -u postgres` without `-U ${ODOO_DB_USER}` (there is no `postgres` role), `kubectl cp` steps (now `scp` and `tar` over SSH), the env-name check that printed values (`compgen -e` lists names only), and the master-password check that printed the plain-text `admin_passwd`. `reference/configuration.md` describes the Odoo image's new `addons_path` pattern for `/mnt/extra-addons`. `tests/odoo-skill-commands.test.sh` fails on any of those command shapes, and `tests/odoo-backup-script.test.sh` runs `backup.sh` against fake `odoo`, `pg_dump` and `ssh` binaries. `backup.sh` now says where the backup lives: on Odoo's data volume, which survives restarts (the old "copy it off the container to keep it" led the assistant to tell a customer the folder wasn't persistent). Every other `odoo` command given `-d` now passes `-c /etc/odoo/odoo.conf` as well: under `sudo`, `odoo neutralize -d <db>` without it ends "THE DATABASE IS NOT NEUTRALIZED!" (checked on the rig's Odoo 19 pod), and `SKILL.md` rule 2 now leads with installs that run while Odoo serves. Tenants get this once it reaches `main`.
- **gibbon** (0.1.2): fixed `scripts/backup.sh` failing on every run with exit 2 (`mysqldump: [ERROR] unknown option '--skip-ssl'`). The scripts hardcoded MariaDB's `--skip-ssl`, but on the Magneto Agent's Ubuntu 24.04 base `default-mysql-client` is Oracle MySQL 8.0, which only takes `--ssl-mode`. `verify-health.sh` and `php-info.sh` had the same flag, and since they send mysql stderr to `/dev/null`, every DB check failed silently. The new `scripts/lib/mysql-tls.sh` reads the installed client's `--help`. For MySQL it passes `--ssl-mode=DISABLED --get-server-public-key`: without the key flag, a non-TLS `caching_sha2_password` login fails with ERROR 2061 when the server's auth cache is cold, e.g. after a gibbon-mysql restart. For MariaDB it keeps `--skip-ssl`, which 11.4+ still needs because it rejects the server's self-signed cert. `scripts/tests/mysql-tls.test.sh` is a hermetic test that runs all three scripts against fake clients of both flavours.
- **ai-studio** (0.2.1), **gibbon** (0.1.1), **moodle** (0.1.2), **odoo** (0.1.1), **wordpress** (0.1.2): the AI Assistant's model key is now Clouve-managed, one key per deployment, delivered to the Magneto Agent as `MAGNETO_AGENT_LLM_KEY` and exported to Claude Code as `ANTHROPIC_AUTH_TOKEN`. The tenant key file `~/.claude_api_key`, the key prompt and the Preferences panel are gone. Each `SKILL.md` key-protection rule now names the managed key; gibbon's `rotate-admin-credentials` playbook section 3 says Clouve rotates it and lists where it lives; gibbon/odoo `learnings.md`, gibbon `reference/shell-access.md` and moodle `reference/observability.md` match. The ai-studio description drops the retired "agent client selection".
- Dropped Codex CLI and Gemini CLI from `README.md` and the `marketplace.json` description: the AI Assistant runs Claude Code only.
- **wordpress** (0.1.1): channel-reality update — the Clouve-packaged WordPress app is now agent-enabled (magneto `develop` commit `7f4e6ca`: `x-clouve-agent` block + `clouve-ops` sshd in BOTH sibling images + per-app persona + `mariadb:12.3` pin). The same change ships `clv-docker-compose-basic.yml`, so packaged WordPress publishes TWO listings from one image pair: "WordPress" (basic, agent-off — sshd never starts because `CLOUVE_OPS_PASSWORD` is not injected, i.e. shell-less like before) and "WordPress with AI Assistant" (agent-enabled). On the agent-enabled listing the `clouve-ops` SSH probe is now EXPECTED GREEN and wp-cli is reachable (`sudo -u www-data wp --path=/var/www/html …`); verified live on a Kubernetes deployment (SSH + sudo both siblings, wp-cli 6.9, `verify-health.sh` GREEN). `learnings.md` entry updated; vanilla developer composes remain shell-less and probe-first semantics are unchanged.
- **wordpress** (0.1.0): new DevOps plugin — safely operate a WordPress site deployed on Clouve (backups/restores, plugin and theme management, core updates, site URL changes, wp-cron, hardening, diagnosing WSODs/500s/lost admin access). Grounded in the Clouve-packaged image's installer entrypoint behavior (boot-time `siteurl`/`home` reconciliation from `WORDPRESS_SITE_URL`, forced `WP_DEBUG_DISPLAY` off, uploads re-chown, hardcoded `wp_` install detection) with a do-not-fight list. Ships `install.sh` (default-mysql-client + openssh-client + sshpass, moodle-pattern).
