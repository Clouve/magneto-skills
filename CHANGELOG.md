# Changelog

## Unreleased

- **wordpress** (0.1.6): wp-cli over the clouve-ops shell couldn't reach the database. The image's `wp-config.php` reads WordPress's database settings from the container's environment, and an SSH session doesn't inherit it, so every wp command that loads the database stopped with "Error establishing a database connection". On the rig on 2026-11-03, `scripts/temp-password.sh` changed nothing in its plain mode for that reason. The new `scripts/wp.sh` runs one wp command as `www-data` with the `WORDPRESS_*` settings of the container's first process (`/proc/1/environ`, read through sudo as that process's owner), handed to wp in its environment, so no value is on a command line. It hands wp only the settings `wp-config.php` reads, and refuses `config list` and `config get` of the database password, a key or a salt, which would print them into the chat. `temp-password.sh` runs wp the same way (`scripts/lib/wp-remote.sh`), and every wp command in the playbooks and references now goes through `wp.sh`. `temp-password.sh`'s sign-in check also posted to the container's own address over plain HTTP, and when the site's address is https, WordPress redirects that request to HTTPS before it looks at the password, so the check could never confirm a sign-in. It now posts to `WORDPRESS_SITE_URL`'s `wp-login.php` when that address is https, and to the container otherwise, so a password sent in clear stays inside the cluster. When nothing answers, its line says why. Every ssh and scp command in the skill passes `StrictHostKeyChecking=accept-new` and `UserKnownHostsFile=/dev/null` now: a rebuilt image has new host keys, and on an agent with no SSH settings of its own for the app's containers, a command without them stops at a saved key that no longer matches, or at a prompt sshpass can't answer. `tests/wordpress-channel-text.test.sh` checks them with `tests/lib/ssh-host-key-check.py`. Tests: `tests/wordpress-wp-runner.test.sh` is new, and the stand-ins in `tests/wordpress-temp-password.test.sh` now act as sshd, sudo and wp-cli do: a session without the container's environment, an environment that sudo resets, and no database without WordPress's settings.
- `CLAUDE.md` says that a plugin added or changed updates its row in `README.md`'s Plugins table, and `tests/plugin-versions.test.sh` also fails when a row's category isn't the catalog's or its description is empty.
- **odoo** (0.1.4): the skill said Odoo is PID 1 in its container. In the Odoo images built from 2026-11-02 on (magneto `apps/odoo/image/`), tini is PID 1 and Odoo is its child: tini reaps the processes that finished SSH sessions leave behind, which Odoo never did, and passes signals on to Odoo. The restart command stays `grep -q odoo /proc/1/cmdline && sudo kill -HUP 1`, since tini's command line has `odoo` in it too and older images still run Odoo as PID 1. `SKILL.md`, `reference/stack-and-runtime.md`, the install playbook and `learnings.md` now say so, and every restart the skill gives checks `/proc/1/cmdline` first. `SKILL.md` and `reference/stack-and-runtime.md` also warn that Odoo's command line holds the database password, so the assistant never runs `ps aux` or anything else that prints it. The database-manager playbook had the assistant type a new master password into an `odoo shell` command, where it showed in the chat and in the container's process list; now the tenant sets it on Odoo's own Set Master Password page. The log text no longer sends anyone to a log view the tenant doesn't have: Odoo's log is the container's own output, which Clouve support reads. Neither new image holds SSH host keys: each container makes new ones when it starts, so a key the agent saved is wrong after the next restart, and ssh refuses it. The skill passed `-o StrictHostKeyChecking=accept-new` on a "first connection" and relied on the saved key after that. Now every `ssh` and `scp` in its playbooks, references and scripts also passes `-o UserKnownHostsFile=/dev/null`, which saves nothing, so the commands work on older agents too (newer agents' own SSH settings keep no key for their sibling containers). `tests/odoo-channel-text.test.sh` fails on "Odoo is PID 1", on a line about PID 1 that doesn't name tini, on text that relies on a saved host key, on a SIGHUP in any spelling that isn't the checked restart command, on a restart command whose check would skip Odoo on either image or signal PostgreSQL, on a command that prints a process's arguments, on a master password typed into a command, and on any `ssh` or `scp` command, a scp upload or a command in backticks in the prose included, whose options, run through `ssh -G` with no config file, would save or check a host key (`tests/lib/ssh-host-key-check.py`, which the gibbon test uses too). Tenants get this once it reaches `main`.
- **gibbon** (0.1.4): a new `playbooks/add-a-user.md` for adding a teacher, a student or a parent. On the Education Kit shoot the assistant had no playbook for this and wrote a raw `gibbonPerson` insert, with about 50 empty columns and a hand-made password hash. Now it checks that the username is free, agrees the role with the admin, and sends the admin to Gibbon's own form (User Admin, Manage Users, Add) with a link built from the install's own tables. Then it checks the new row, says what the person still needs (a student's enrolment, a parent's family, a staff record), and keeps every password out of the chat. The playbook has no SQL path, and a username the admin types reaches SQL only as a hex literal, so a quote in it can't change the query. In the Education Kit it says that only students and staff with status Full get a Moodle account (never a parent) and runs Moodle's user sync with the admin's go-ahead. Moodle then emails the new person a password, or the admin sets one in Moodle's own form; the assistant never sets, asks for or sees it. `SKILL.md` gets operating principle 11 and a safety gate for it. The skill also stops saying the assistant can't write into the gibbon container; the clouve-ops channel lets it. Backups archive `uploads/`, `config.php` and `customAssets/` over SSH, restores put them back the same way, a module goes in as the very folder the assistant audited, and `config.php`, the cron log and `service cron status` are checked in the container, with `config.php` never printed. `reference/shell-access.md` now says that Apache's error log is the container's own output, which nothing in the pod can read: `php:8.3-apache` links it to stderr, so the skill no longer sends the assistant to tail it. `scripts/backup.sh` passes `--no-tablespaces` to `mysqldump`, as do the dump commands in the playbooks and references, so the gibbon user no longer needs the PROCESS privilege and the dump prints no warning. Every `ssh` passes `-o StrictHostKeyChecking=accept-new -o UserKnownHostsFile=/dev/null`, as the odoo skill's do: on an agent without the 4.5.3 image's settings for its sibling containers, a host key it didn't know stopped `sshpass` without a word (exit 6), so a backup's files archive came out empty, and a rebuilt image's new key would be refused. `reference/shell-access.md` says so instead of "accept it interactively". Other changes: `diagnose-500.md` reports only whether `config.php` parses (`php -l` names the token where it stopped, which can be part of the password), a full restore asks for the ack before it replaces any file, with `config.php` compared by `sha256sum` (and the gates table has a row for it), the backup reference says that Additional modules' code isn't in the archive and points to the deployment's Backups tab, every `mysql` and `mysqladmin` command takes its password in `MYSQL_PWD`, `reference/security.md` no longer gives a recipe for writing a password hash, the log text sends a question about Apache's log to Clouve support, and the description mentions adding people. Lines that had the user restart the app or the container, or check a pod list or a platform dashboard, none of which the user's Clouve dashboard has, now say what the admin can do in Gibbon, what the assistant can do over the clouve-ops channel, or to ask Clouve support. When a restored `config.php` holds older database settings, the assistant offers to put back the `config.php` it kept just before the restore, with the user's ack. The Kit section says the new person's Moodle password comes within a few minutes, since Moodle's cron runs every five minutes there. `tests/gibbon-add-user.test.sh` and `tests/gibbon-channel-text.test.sh` cover the playbook, the stale lines, the ssh options (through `ssh -G`), `php -l`, the restore's order and the restart lines, and `scripts/tests/mysql-tls.test.sh` checks the flag.
- **moodle** (0.1.7): `scripts/backup.sh` and the dump commands in `reference/backup-restore.md` and `playbooks/rollback-from-backup.md` pass `--no-tablespaces` to `mysqldump`. Without it, the agent's MySQL 8 client asks for tablespace information, which needs the PROCESS privilege the moodle user doesn't have, and every backup printed a warning. Moodle creates no tablespaces, so the dump loses nothing. The playbook's forensic dump, and nine `mysql` commands in the skill (the rollback's restore among them), gave the password as `-p"..."`, where `ps` shows it for as long as the command runs; every one now takes it in `MYSQL_PWD`. `SKILL.md` and the password playbook said Moodle's cron runs every minute here. On the Clouve app and in the Education Kit it runs every five minutes (the image's default, since neither sets `MOODLE_CRON_INTERVAL`), so a password set for a synced user without clearing `create_password` stops working within five minutes, not one. `tests/moodle-backup-script.test.sh` runs `backup.sh` against a fake `mysqldump`, and `tests/mysqldump-no-tablespaces.test.sh` checks every gibbon, moodle and wordpress dump for the flag and every `mysql`, `mysqladmin` and `mysqldump` command for a password on its command line.
- **wordpress** (0.1.5): the skill said the WordPress images ship no sshd, so the assistant expected its SSH probe to fail and planned without wp-cli. Both Clouve images have shipped the `clouve-ops` sshd since 2026-08-05, and it runs whenever the AI Assistant does. The playbooks and references now lead with the shell on the Clouve app (wp-cli as `sudo -u www-data wp --path=/var/www/html`), keep the TCP/HTTP paths for a developer's own compose or a failed probe, and `reference/shell-access.md` lists the failure modes. A password reset runs through the new `scripts/temp-password.sh` (below), the OPcache step uses `sudo apachectl graceful` instead of PHP-FPM's `kill -USR2`, the three markdown dumps pass `--no-tablespaces`, the MariaDB image is described as pinned (`mariadb:12.3`), and the 2026-08-05 learnings entry now lives in the references. `scripts/temp-password.sh` gives an account a temporary password that never reaches the chat or a command line. It makes the password and saves it to a mode 600 file in `~/wordpress-passwords` (the Files pane shows it) before WordPress changes, then hands it to `wp user update` on stdin over the shell, with wp's output thrown away in the WordPress container, since wp-cli prints a value it reads for `--prompt`. With `--via-db` it writes the MD5 value over TCP-mysql instead. It reads the account back, tries the password at `wp-login.php` with it on curl's stdin, and prints only the file's name. It counts that sign-in as accepted only when WordPress sets its logged-in cookie and redirects to wp-admin: with `FORCE_SSL_ADMIN` on, or a plugin that hides `wp-login.php`, WordPress redirects before it checks the password, and the line then says it couldn't confirm the sign-in. The admin hands the password over from the file, and `--remove` deletes it. 0.1.4 put the password on the remote command line and kept it in a shell variable, which doesn't survive between the assistant's Bash calls. Also: `WP_DEBUG_LOG` goes to `/tmp/wp-debug.log`, outside the docroot, since `wp-content/debug.log` can be fetched by anyone; the wp-cli commands that deactivate a broken plugin pass `--skip-plugins` (and `--skip-themes` for all of them), so a plugin that fatals on load can't kill them; and the text no longer sends the user to pod logs or to a restart their dashboard doesn't have: those lines now say what the user can do, what the assistant can do over the shell or the database, or to ask Clouve support. `tests/wordpress-temp-password.test.sh` runs the script against stand-ins, a `wp` that prints what it reads included, and fails if the password reaches its output, the channel back from the container, any command line or any environment, if a redirect without WordPress's sign-in cookie counts as accepted, or if the session cookie in WordPress's answer is printed or left in a file. `tests/wordpress-channel-text.test.sh` fails on the old no-sshd phrasing, on a password kept in a shell variable or given to wp-cli directly, on a password playbook whose commands write `user_pass` themselves, on text that says a 302 alone means a password works, and on a restart, a pod list or a platform dashboard the user doesn't have.

- **nextcloud** (0.1.0): new DevOps plugin for the Clouve Nextcloud app (`apps/nextcloud` in Clouve/magneto, Nextcloud 35.0.2). With it the AI Assistant manages staff accounts and groups, Team folders, quotas and store apps, backs up and restores the server, checks its health, and recovers from a stuck upgrade or maintenance mode. It works over three channels. `occ` runs as `www-data` over the `clouve-ops` SSH account on the Nextcloud container and does most of the work. HTTP to `${NEXTCLOUD_HOST}` with the public `Host:` header covers only what `occ` can't: the main admin's own shares and the health probes. Read-only SQL over TCP is for diagnostics. The skill ships seven scripts: `occ.sh` runs one `occ` command with safe quoting, `verify-health.sh` reports GREEN, AMBER or RED, `run-in-nextcloud.sh` sends `backup.sh` and `restore.sh` into the container, `share-as-admin.sh` creates, lists and revokes shares of the main admin's own files, and `temp-password.sh` gives an account a temporary password. Passwords never reach a command line or the chat. They go in on stdin (`occ.sh --password-stdin`, curl's `-K -`) or in `MYSQL_PWD`, a temporary password is written to a mode 600 file in the agent user's home with only the file name printed, and the assistant never asks for a password in chat. SMTP setup stays with the admin, who fills in Nextcloud's own form, and the skill says plainly what this deployment doesn't offer (an Office server, antivirus, full-text search, the web updater). Tenants get it once it reaches `main`.
- **moodle** (0.1.6): `scripts/verify-health.sh` reported RED on every Kubernetes deployment, from three bugs in its own code. The login-page probe went to `http://${MOODLE_HOST}`, and Moodle answers any host but its `wwwroot`'s with a 303: the probe now sends `Host:` with the host of `MOODLE_URL` (with an https URL the image sets `$CFG->sslproxy`, so the host is all Moodle checks). The code version came from a one-liner whose `$CFG` the remote shell expanded to nothing, and even quoted right it would have read the database's version: the script now reads `$version` from `version.php` on the sibling (`public/` first, as the image does), with the commands sent to `bash -s` on stdin, and compares versions as numbers (`2026042000.00` in the file, `2026042000` in `mdl_config`). The cron check did shell arithmetic on `MAX(timestart)`, a decimal column, and stopped with a syntax error: it now uses whole seconds. `reference/shell-access.md` gives the probe with the `Host:` header too. `tests/moodle-verify-health.test.sh` runs the script against fake `curl`, `mysql`, `sshpass` and `php`, with the remote commands run by a real bash.
- **ai-studio** (0.2.3), **gibbon** (0.1.3), **moodle** (0.1.5), **odoo** (0.1.3), **wordpress** (0.1.4): passwords are no longer in the AI Assistant's environment on new Magneto Agents. The agent keeps them in `/run/clouve/secrets.env`, and `clv-secret NAME` prints one. Skills reach every agent from git, and older agents still have the password in the environment and no `clv-secret`, so every command now fetches a password as `${NAME:-$(clv-secret NAME)}`. That works on both: an agent that has `NAME` never runs the second half. Each script that uses an agent-side secret loads it once near the top with `: "${NAME:=$(clv-secret NAME)}"`. The `:` keeps the line safe under `set -e`, and the line has no `2>/dev/null`, so `clv-secret`'s own messages ("waiting for the agent to finish connecting to its apps...", "NAME is not set on this server") reach whoever ran the script. Each `SKILL.md` says in its environment section that passwords aren't in the environment and that `clv-secret --list` shows the names. Lines that called a password "already in your env", or told the assistant to pass one as `$(printenv NAME)`, now describe `clv-secret`, and prose that only names a variable uses the bare name. In the WordPress playbooks and references, each `compgen -e | grep` step has a `clv-secret --list | grep` line for the passwords' names, and the script messages that sent the reader to `compgen` for a password's name say `clv-secret --list`. moodle's and wordpress's `learnings.md` get the "Secrets. Ever." line that gibbon's and odoo's already had. `CLAUDE.md` has the secrets contract. `tests/skills-env-values.test.sh` fails on a bare `$NAME` of an agent-side secret, a script without its loader line, `printenv` of a secret, and prose that calls a password "already in your" environment.

- **odoo** (0.1.2): fixed the backup and install steps that stalled the AI Assistant on 2026-10-19. The playbooks ran `scripts/backup.sh` from `/var/lib/odoo/scripts/`, which no Odoo container has. The assistant now pipes the skill's own copy into the Odoo container (`sshpass -e ssh ... - **gibbon** (0.1.2): fixed `scripts/backup.sh` failing on every run with exit 2 (`mysqldump: [ERROR] unknown option '--skip-ssl'`).
