# Architecture

The single most load-bearing fact about the Clouve-packaged shape: **the boot sequence is not the stock one.** A custom installer entrypoint wraps the official image's entrypoint and actively reconciles state — site URL, debug display, uploads ownership — from the `WORDPRESS_*` env on **every boot**. The env (i.e. the platform) is the authority; a hand change the entrypoint covers is silently reverted at the next restart. Learn the sequence below so you work *with* the reconciler, never against it.

The developer-submitted shape has none of this — stock entrypoint, stock lifecycle, nothing reconciled. Establish the shape first ([stack-and-runtime.md](stack-and-runtime.md)).

## Request lifecycle (both shapes — standard WordPress)

1. **Apache** (port 80 in-container; TLS terminates at the platform ingress, not here) receives the request. `.htaccess` rewrite rules route pretty permalinks to `index.php`.
2. `index.php` → `wp-blog-header.php` → **`wp-load.php`**, which locates and requires **`wp-config.php`**.
3. `wp-config.php` defines the DB constants (`DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`), `$table_prefix`, salts, and any `WP_*` flags, then requires **`wp-settings.php`** — the real bootstrap.
   - On both shapes the file was generated by the official image's entrypoint from the `WORDPRESS_*` env. In current official images the generated file reads the env *at request time* through a `getenv` wrapper (standard official-image behavior), so a changed `WORDPRESS_DB_PASSWORD` takes effect on container restart without anyone rewriting the file.
4. `wp-settings.php` connects to the DB, loads must-use plugins, then active plugins (from `wp_options.active_plugins`), then the active theme (from `template`/`stylesheet`), fires init hooks, parses the query, and dispatches to the template. This ordering is why a fatal in any single active plugin can take down every page — and why the WSOD isolation trick works at the `active_plugins` option ([data-model.md](data-model.md)).
5. On page loads WordPress may also spawn a loopback request to `wp-cron.php` to run due scheduled events — cron is traffic-driven, not a daemon ([cron-and-tasks.md](cron-and-tasks.md)).

Failure mapping: DB unreachable → "Error establishing a database connection" (step 4, before plugins load); fatal in a plugin/theme → 500/WSOD (mid step 4); `.maintenance` file present → "Briefly unavailable for scheduled maintenance" (checked early in bootstrap). See [troubleshooting.md](troubleshooting.md).

## Where things live on disk

Full tree in [stack-and-runtime.md](stack-and-runtime.md). The operationally load-bearing paths:

| Path | What it is | Reachable today via |
|---|---|---|
| `/var/www/html/wp-config.php` | DB creds, salts, `WP_*` flags | Nothing (file channel only) — prefer the env-driven path on Shape A ([configuration.md](configuration.md)) |
| `wp-content/plugins/`, `themes/` | Code on disk; the DB only holds *which* are active | [HTTP] existence probes; install/manage via `/wp-admin` |
| `wp-content/uploads/` | Media; DB references it by URL/path | [HTTP]; Shape A re-chowns it every boot |
| `wp-content/debug.log` | PHP error log when `WP_DEBUG_LOG` is on | Enabling needs a file channel (none today); reading is [HTTP]-fetchable when the file exists — it sits in the docroot ([diagnose-500 playbook](../playbooks/diagnose-500.md)) |
| `.maintenance` | Update-in-progress marker | Removal needs a file channel — none today; say so and route |
| `.htaccess` | Permalink rewrites | Regenerated by a rewrite flush; Shape A hard-flushes at boot after URL heal |
| The database | Everything else: content, users, options, transients | **[TCP-mysql] — your widest channel** ([data-model.md](data-model.md)) |

## The Clouve installer entrypoint, step by step (Shape A only)

Source: [apps/wordpress/image/installer/entrypoint.sh](https://github.com/Clouve/magneto/blob/develop/apps/wordpress/image/installer/entrypoint.sh). It runs as root, under **`set +e`** — errors are logged, not fatal, and Apache starts anyway (except the two explicit `exit 1` steps below). A Running pod therefore does **not** imply a healthy install; verify with [scripts/verify-health.sh](../scripts/verify-health.sh).

1. **Official entrypoint, time-boxed.** Runs the untouched official `docker-entrypoint.sh` in the background for a fixed `sleep 5`, then kills it. In those 5 seconds the official script extracts core files into `/var/www/html` and generates `wp-config.php` from the `WORDPRESS_*` env. **The fixed 5s is a race on slow volumes** — see [install-and-bootstrap.md](install-and-bootstrap.md) for the failure signature.
2. **DB wait.** Up to 60 × 5s attempts of `mysql -h $WORDPRESS_DB_HOST -e "SELECT 1"`; `exit 1` on timeout (container restarts, loop repeats).
3. **Core sanity check.** `exit 1` if `/var/www/html/wp-load.php` is missing — the step-1 race lost.
4. **Install detection.** `SELECT 1 FROM wp_options` — the `wp_` prefix is **hardcoded**, ignoring `WORDPRESS_TABLE_PREFIX`. There is no marker file; the `wp_options` table *is* the install state. A non-default prefix therefore makes every boot conclude "not installed" and run a fresh `wp core install` into the same database — a second site alongside the first. This is why [SKILL.md](../SKILL.md) principle 10 says never change the prefix.
5. **URL self-heal (installed path).** If installed and `WORDPRESS_SITE_URL` is set: compares `wp option get siteurl` / `home` against the env; on mismatch runs `wp option update` for both plus `wp rewrite flush --hard`. **The env var wins every restart.** Only those two options are healed — URLs embedded in post content, widgets, and page-builder blobs still need a deliberate serialization-aware search-replace ([urls-and-migration.md](urls-and-migration.md)).
6. **Fresh-install path (not-installed).** `wp core install --url --title --admin_user --admin_password --admin_email --skip-email --allow-root` from the `WORDPRESS_*` env, then timezone `UTC`, permalink structure `/%postname%/`, and a hard rewrite flush.
7. **Debug display forced off — both paths, every boot.** `wp config set WP_DEBUG_DISPLAY false --raw`. Don't expect on-screen errors to persist; debug via `WP_DEBUG` + `WP_DEBUG_LOG` instead ([configuration.md](configuration.md)).
8. **Uploads ownership — every boot, uploads only.** `mkdir -p wp-content/uploads`, `chown -R www-data:www-data`, `chmod -R 755` — on `wp-content/uploads` **only**. Root-owned files elsewhere in `wp-content` (left by `--allow-root` wp-cli operations) persist and break in-app updates later; whenever wp-cli runs as root, chown after.
9. **No system cron — then `exec apache2-foreground`.** Neither image ships cron; `wp-cron.php` fires on HTTP traffic only. The 10s healthcheck gives a de-facto heartbeat, so schedules on a packaged deploy drift less than folklore suggests — but it is still traffic-driven ([cron-and-tasks.md](cron-and-tasks.md)).

## Do not fight the entrypoint

Every one of these is a real operator instinct that the boot sequence silently defeats:

| Tempting action | What actually happens | Do instead |
|---|---|---|
| `UPDATE wp_options SET … WHERE option_name IN ('siteurl','home')` by hand | Reverted from `WORDPRESS_SITE_URL` at next boot (step 5) | Domain changes go through the platform; [change-site-url playbook](../playbooks/change-site-url.md) |
| Turn on `WP_DEBUG_DISPLAY` to see errors | Forced off every boot (step 7) | `WP_DEBUG` + `WP_DEBUG_LOG` (enabling needs a file channel; reading an existing log is HTTP-fetchable — be honest about the enabling gap) |
| Fix a permissions mess with one chown, assume it sticks | Only `uploads/` is re-asserted (step 8); the rest of `wp-content` keeps whatever damage exists | Chown deliberately after any root-run wp-cli, when a shell exists |
| Change `WORDPRESS_TABLE_PREFIX` | Double-install into the same DB (step 4) | Refuse — [SKILL.md](../SKILL.md) gate |
| Rely on "the pod is Running" as health | `set +e`: Apache starts over a half-failed install | [scripts/verify-health.sh](../scripts/verify-health.sh) |
| Expect a cron daemon | There isn't one, either image (step 9) | [cron-and-tasks.md](cron-and-tasks.md) |

## Shape B contrast

On a developer-submitted compose the lifecycle is the stock official-image one: entrypoint extracts core and writes `wp-config.php` on first boot, then execs Apache. First boot with an empty DB serves the browser installer at `/wp-admin/install.php`; nothing reconciles `siteurl`/`home` ever (a wrong value locks `/wp-admin` — [SKILL.md](../SKILL.md) principle 4); debug flags stay however they were set; no uploads re-chown; no cron either. Everything in the "do not fight" table above becomes "there is no reconciler — you own the consequences directly."
