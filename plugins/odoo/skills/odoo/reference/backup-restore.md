# Backup & Restore

## What an Odoo backup contains

A complete backup is not just a database dump. The canonical ZIP backup contains three things
(`odoo/service/db.py`, `dump_db()`):

1. **`dump.sql`** — plain-text `pg_dump --no-owner` of the PostgreSQL database.
2. **`filestore/`** — the per-DB binary filestore (`<data_dir>/filestore/<dbname>/`), which
   holds content-addressed attachments (`sha1[:2]/sha1` layout). Files stored in the
   filestore are NOT in the database.
3. **`manifest.json`** — metadata written by `dump_db_manifest()`: Odoo version,
   `version_info`, `major_version`, `pg_version`, installed module list with versions.

A backup produced with `--format dump` (the `dump` format) is a PostgreSQL **custom-format**
`pg_dump -F c` of the DB only — **no filestore, no manifest**. This format is useful for
DBA-level DB-only restores; it is an incomplete Odoo backup.

A hand-rolled `pg_dump` alone is also incomplete: it misses the filestore and manifest.

## Restore mechanics (service/db.py `restore_db()`)

`restore_db()` branches on whether the input is a ZIP:

- **ZIP (v8+ format):** creates the DB, runs `psql -q -f dump.sql`, then moves the extracted
  `filestore/` into the correct data-dir location.
- **Non-ZIP (legacy ≤7.0 / raw pg_dump):** creates the DB, runs `pg_restore --no-owner`.

**No version check at restore time.** `restore_db()` does not verify Odoo version
compatibility before restoring. The `list_db_incompatible()` check only appears on the
HTTP database manager page — it is informational only and is not enforced at restore.

**Refuses to overwrite an existing database.** `restore_db()` calls `exp_db_exist()` first;
if the target DB already exists it raises `"Database already exists"` and aborts.

## CLI vs HTTP — prefer the CLI

### odoo-bin db subcommand (preferred)

The `odoo-bin db` subcommand (`odoo/cli/db.py`) is filestore-aware, **bypasses the master
password entirely**, and internally forces `list_db=True` so `check_db_management_enabled`
does not block it.

**Give the config as `ODOO_RC`, not `-c`.** The `db` command registers `-c/--config` on its
own parser (`cli/db.py:39`), so `-c` parses only between `db` and the subcommand. After the
subcommand it is an error ("unrecognized arguments: -c"), and before `db` the whole line goes
to the server parser ("unrecognized parameters: db dump ..."). Other subcommands want `-c`
elsewhere: `odoo module install -c ...` takes it after `install`. `ODOO_RC` works the same for
every subcommand. Over the clouve-ops channel you need it anyway: `sudo` drops the `ODOO_RC`
the image sets, and with no config Odoo looks for PostgreSQL on a local socket and fails.
The installed command in this container is `odoo` (there is no `odoo-bin` on the PATH).

```
# Inside the Odoo container (over the clouve-ops channel, put sudo in front):
ODOO_RC=/etc/odoo/odoo.conf odoo db dump <dbname> /tmp/<dbname>.zip
ODOO_RC=/etc/odoo/odoo.conf odoo db load -n <dbname> /tmp/<dbname>.zip
ODOO_RC=/etc/odoo/odoo.conf odoo db duplicate -n <source> <target>
```

The skill's [scripts/backup.sh](../scripts/backup.sh) wraps the dump and checks the ZIP; see
[playbooks/backup.md](../playbooks/backup.md) for how to pipe it into the container.

### db dump

```bash
# ZIP format (default, includes filestore + manifest):
ODOO_RC=/etc/odoo/odoo.conf odoo db dump <dbname> /tmp/<dbname>.zip

# Dump-only format (pg_dump custom, DB only, no filestore):
ODOO_RC=/etc/odoo/odoo.conf odoo db dump --format dump <dbname> /tmp/<dbname>.dump

# Dump without filestore (ZIP with dump.sql + manifest.json but no filestore/):
ODOO_RC=/etc/odoo/odoo.conf odoo db dump --no-filestore <dbname> /tmp/<dbname>.zip
```

### db load

```bash
# Restore from ZIP to a new DB (new dbuuid generated by default):
ODOO_RC=/etc/odoo/odoo.conf odoo db load <dbname> /tmp/<dbname>.zip

# Restore and neutralize immediately (MANDATORY for prod→staging clones):
ODOO_RC=/etc/odoo/odoo.conf odoo db load -n <dbname> /tmp/<dbname>.zip

# Restore as a "move" (keep original dbuuid, not a copy):
ODOO_RC=/etc/odoo/odoo.conf odoo db load --move <dbname> /tmp/<dbname>.zip

# Force-overwrite an existing DB (drops it + rmtree filestore — irreversible):
ODOO_RC=/etc/odoo/odoo.conf odoo db load -f <dbname> /tmp/<dbname>.zip
```

**Flag semantics:**
- Default (no `--move`): a new `dbuuid` is generated (the copy/restore-as-copy path).
- `--move`: keeps the original dbuuid (treat as a moved DB, not a clone).
- `-n` / `--neutralize`: neutralizes the DB after restore. Mandatory for prod→staging.
- `-f` / `--force`: drops the target DB and removes its filestore directory before loading.
  This is irreversible — the old DB and its files are gone.

**Note (`cli/db.py:232-235`):** `db load` only accepts ZIP files. If given a raw pg_dump
file it exits with: `"Not a zipped dump file, use pg_restore to restore raw dumps, and
psql to execute sql dumps or scripts."`

### db duplicate

```bash
# Duplicate (server-side PG CREATE DATABASE ... TEMPLATE, copies filestore):
ODOO_RC=/etc/odoo/odoo.conf odoo db duplicate <source> <target>

# Duplicate and neutralize (recommended for staging):
ODOO_RC=/etc/odoo/odoo.conf odoo db duplicate -n <source> <target>
```

### db drop

`db drop` runs `DROP DATABASE` **and** `shutil.rmtree` on the filestore directory.
Both the DB and the filestore files are permanently removed.

## HTTP /web/database/backup and /web/database/restore

The HTTP routes (`addons/web/controllers/database.py`) require:
- `list_db=True` in the Odoo config (the routes are blocked by `check_db_management_enabled`).
- `master_pwd` (the admin password) passed in every POST body.

They call the same `dump_db()` / `restore_db()` functions as the CLI but without the
master-password bypass. The restore route declares `max_content_length=None` — there is no
server-side upload size limit (enforce this at the ingress/proxy level if needed).

## What the filestore is

`<data_dir>/filestore/<dbname>/` — two-level content-addressed tree: each file is stored at
`<sha1[:2]>/<sha1>`. References in `ir.attachment` point to these paths. Missing filestore
files read back as empty bytes (no hard error), so a DB restored without its filestore
appears to work but silently loses all attachments, images, and binary fields stored as
files rather than in the DB column.

## Checklist before a restore

1. Confirm the target DB does not exist (restore refuses to overwrite).
2. Confirm you have both `dump.sql` AND the `filestore/` (if you took a ZIP backup,
   both are in the ZIP).
3. If restoring to staging/test, add `-n` to neutralize immediately — never run a clone
   that can email customers or charge payments.
4. After restore, verify attachment counts and spot-check a record with an attachment to
   confirm the filestore moved correctly.
